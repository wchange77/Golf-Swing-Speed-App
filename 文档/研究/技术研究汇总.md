## 1. iPhone 激光雷达传感器

### 1.1 iPhone 激光雷达的工作原理（dToF、VCSEL、SPAD）

iPhone LiDAR 是一个**直接飞行时间 (dToF)** 系统，具有三个核心组件：

**VCSEL 发射器（垂直腔表面发射激光器）：**
- 底部发射 VCSEL 光源，工作波长为 **940nm**（近红外）
- iPhone 12/13 Pro：16 组 4 个 VCSEL 单元 = 总共 64 个，乘以 3x3 衍射光学元件 (DOE) 以产生 **576 个激光脉冲**
- iPhone 15 Pro：重新设计的模块，将有效芯片面积减少了三分之一以上，并消除了衍射光学器件
- VCSEL 非常适合移动设备：尺寸小、功率效率高、波长带宽窄

**SPAD 接收器（单光子雪崩二极管）：**
- 940nm增强型SPAD图像传感器，具有板载距离计算逻辑
- 能够检测**单光子信号**，分辨率可达数十皮秒
- 每个反射脉冲的飞行时间都是单独测量的

**dToF原理：**
- 系统在整个场景中投射结构化图案
- 测量每个激光脉冲的往返时间
- 计算深度=（光速x时间）/2

### 1.2 精度、刷新率、点云密度

|规格|价值|
|---|---|
| **最大范围** | 5米|
| **深度图分辨率** | 256 x 192 像素（约 49,000 个深度点/帧）|
| **刷新率** |高达 60 Hz |
| **绝对准确度** |对于边长 >10 cm 的物体，+/- 1 cm |
| **25 厘米处的点密度** | ~7,225 点/m^2 |
| **250 cm 处的点密度** | ~150 点/m^2 |
| **最小可检测物体** |边长约 5 厘米 |
| **波长** | 940 nm（近红外）|

**关键准确性说明：**
- 准确度和精确度随着各个方向上物体尺寸的增加而增加
- 扫描边长小于 10 厘米的表面时精度会降低
- 误差随着距离的增加而累积；精度下降超过约 2-3 米
- 在采用扫描最佳实践的现实条件下，测量精度在 1-2% 范围内
- 在持续扫描期间，漂移会随着时间的推移而累积

### 1.3 ARKit 深度传感 API

**核心API：**

1. **场景深度（`ARFrame.sceneDepth`）：**
   - 每个`ARFrame` 都包含一个带有两个缓冲区的`ARDepthData` 对象：
     - **深度图**（每个像素=距相机的深度（以米为单位））
     - **置信度图**（每像素置信度：低/中/高）
   - 通过以下方式启用：`ARWorldTrackingConfiguration.supportsFrameSemantics(.sceneDepth)`

2. **场景重建（网格）：**
   - 代表环境拓扑映射的三角形网格
   - 通过将 LiDAR 深度数据与设备上的 ML 融合而构建
   - 可选的语义分类（地板、墙壁、天花板、桌子、座位、窗户、门）
   - 通过会话中的`ARMeshAnchor`对象访问3. **光线投射：**
   - `ARSession.raycast()` — 将光线投射到现实世界
   - LiDAR 改进了 `estimatedPlane` 目标的光线投射
   - 针对对象放置进行高度优化
   - 无需可见特征点即可工作（与仅使用相机的 AR 不同）

4. **点云：**
   - 通过`ARFrame.rawFeaturePoints`直接访问3D点云
   - 激光雷达增强的点云更密集、更准确

### 1.4 用于现实世界测量校准的 LiDAR

**内置校准：**
- RGB 到 LiDAR 校准由扫描应用程序内部处理
- 使用内置算法实时融合深度和图像数据
- 通过`ARCamera`访问内部和外部相机参数

**按用例划分的测量精度：**
- 静态线性读数：1-2 厘米偏差
- 面积测量：~1 m^2 精度
- 采用最佳实践：根据卷尺验证误差在 1-2% 以内

**校准的主要限制：**
- 漂移随着时间的推移而累积（最大的误差源）
- 每次后续扫描都会使错误成倍增加
- 水平表面不如垂直表面准确
- 反光/透明表面会导致错误
- 足以满足架构规划，但不足以满足毫米级工程的要求

### 1.5 激光雷达+相机同时捕捉

**同步 RGB-D 捕捉：**
- ARKit 自动提供每帧同步的 RGB 和深度数据
- RGB 帧：**1920 x 1440** 分辨率
- 深度图：**192 x 256** 分辨率（与 RGB 共同注册）
- 两者均以 **60 Hz** 采样频率捕获
- IMU数据也在每个`ARFrame`中同步

- 使用 `ARWorldTrackingConfiguration` 和 `.sceneDepth` 帧语义
- 每个`ARFrame`包含：RGB图像+深度图+置信度图+相机变换+IMU数据
- 无需手动同步； ARKit 处理时间对齐

**数据流：**
- RGB-D + IMU 数据可以通过 WebSocket 进行流式传输以进行外部处理
- ARKit-Scanner 等项目演示了保存同步颜色、深度和 IMU 数据

### 2.2 用于高 FPS 捕获的 AVFoundation API

**核心管道：**```AVCaptureSession
  ├── AVCaptureDeviceInput (camera)
  └── AVCaptureVideoDataOutput (frame delegate)
        └── AVCaptureVideoDataOutputSampleBufferDelegate
              └── captureOutput(_:didOutput:from:)  → CMSampleBuffer
```
**240fps 捕捉的关键步骤：**
1. 查找 `AVCaptureDeviceFormat`，其 `videoSupportedFrameRateRanges` 包含 240 FPS
2. 锁定设备进行配置
3.设置`activeFormat`为匹配格式
4. 设置`activeVideoMinFrameDuration = CMTimeMake(1, 240)`
5. 设置`activeVideoMaxFrameDuration = CMTimeMake(1, 240)`
6. 禁用平滑自动对焦（如果支持）

**实时帧处理：**
- 实施`AVCaptureVideoDataOutputSampleBufferDelegate`
- 在专用串行调度队列上以 `CMSampleBuffer` 形式交付的帧
- 转换为 `CVPixelBuffer` 以进行 Core ML/视觉处理
- 处理速度必须足够快以避免丢帧

**iOS 17-18 增强功能：**
- `CaptureService` actor 异步管理`AVCaptureSession`
- 零快门延迟、延迟照片处理
- 响应式捕获 API 可减少延迟

### 2.4 实时帧处理流程

**相机帧上的实时 ML 推理架构：**```Camera (240fps) → AVCaptureVideoDataOutput
    → CMSampleBuffer → CVPixelBuffer
        → VNImageRequestHandler (Vision framework)
            → VNCoreMLRequest (Core ML model)
                → Process results
```
**关键考虑因素：**
- 在 240fps 下，每帧处理时间必须小于 4.17ms，以避免丢帧
- 通常每第 N 帧处理一次（例如，每 4 个 = 有效 60fps 推理）
- 使用`alwaysDiscardsLateVideoFrames = true`来防止队列积压
- 在专用串行调度队列上进行处理（不是主线程）
- 直接使用`CVPixelBuffer`以避免复制
- 视觉框架处理 Core ML 的图像预处理（调整大小、标准化）

**优化策略：**
- 在神经引擎上运行 ML 模型（对于大多数模型来说最快）
- 使用量化模型 (Int8) 进行更快的推理
- 管道：在一个队列上捕获，在另一个队列上进行 ML，在主线程上更新 UI
- 考虑使用 `VNTrackObjectRequest` 进行内置对象跟踪

### 2.5 持续捕获期间的热节流

**一般行为：**
- 当内部温度超过阈值时，iPhone 会限制 CPU/GPU
- 持续 240fps 录制会产生大量热量
- 如果检测到过热，录制可能会自动停止

**按世代：**
- **iPhone 12-14 Pro：** 在持续 4K60 录制过程中，热节流明显； 240fps 产生的热量较少（分辨率较低），但几分钟后仍然会受到限制
- **iPhone 15 Pro：** 改进了热管理，但在持续负载下仍然会受到限制
- **iPhone 16 Pro：** 更好的散热架构
- **iPhone 17 Pro：** Apple 设计的激光焊接均热板； GPU 和 CPU 提供高达 **40% 的持续性能提升**

**缓解策略：**
- 拍摄时取下手机壳
- 避免阳光直射
- 保持捕捉会话较短（240fps 时 < 5 分钟）
- 监视代码中的`ProcessInfo.thermalState`（.nominal / .fair / .serious / .ritic）
- 当热状态下降时，适当降低帧速率或停止捕获

## 4. 高尔夫挥杆速度应用程序的要点

### 激光雷达可行性
- **范围：** 对于站在 2-3m 之外的高尔夫球手来说，最大 5m 就足够了
- **刷新率：** 60 Hz 对于直接球杆头跟踪来说太慢（需要 240+ Hz）
- **最佳用途：** 校准场景中的已知距离（例如，发球台位置、球位置），为基于相机的速度计算创建参考系
- **深度图 + RGB 对齐**通过 ARKit 自动实现

### 相机策略
- iPhone 8+ 上 **240fps @ 1080p** 为跟踪快速移动的球杆头提供最佳时间分辨率
- 在 240 fps 下，以 100 英里/小时（约 44.7 m/s）的速度移动的球杆头在帧之间移动 **~18.6 厘米**——仍然非常快，但可能可追踪
- 240fps 的实时 ML 推理需要处理每 N 个帧或使用非常轻量级的模型
- YOLOv3 Tiny 在高尔夫球检测方面达到了 358 FPS，表明球杆检测的可行性

### 推荐方法
1. 使用**LiDAR**进行场景校准（到球的距离、地平面、比例参考）
2. 使用**240fps 相机**进行实际挥杆捕捉和球杆头跟踪
3. 使用 **Core ML** 和量化 YOLO 变体进行球杆头检测
4. 根据像素位移 + LiDAR 校准的真实世界比例计算速度
5. 考虑使用 **TrackNet** 架构来通过运动模糊进行跟踪

### 最相关的开源参考资料
1. **PiTrac** -- 完整的启动监控架构和速度计算逻辑
2. **AICaddy** -- 6000+俱乐部头像图片，YOLOv8训练模型
3. **TrackNet** -- 用于跟踪快速/微小运动物体的最先进技术
4. **Roboflow Golf-club-tracking**——即用型带注释数据集
5. **ARKit-Scanner** -- 演示同步 RGB-D 捕获管道
